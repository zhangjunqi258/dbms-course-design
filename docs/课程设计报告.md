## 一、实验目的

数据库原理课程设计要求基于 C/C++、Java 等程序设计语言，结合数据库原理、编译技术和文字处理技术设计一个 DBMS 系统，帮助学生巩固数据结构、算法、程序设计的基础知识。通过本课程设计，加强学生对数据库管理系统的内部机制的理解，学习 DBMS 的实现技术。

本项目的具体目的：

1. 理解数据库管理系统“存储层—语义层—界面层”的分层结构；
2. 掌握表结构模式（元数据）与表记录在磁盘文件中的自定义存储格式设计方法；
3. 掌握 SQL 语句的词法分析、语法分析与执行的基本实现思路；
4. 掌握关系代数中“选择、投影、连接”运算在程序中的实现方法；
5. 通过小组协作完成一个完整系统，锻炼团队分工与工程实践能力。

## 二、实验要求

1. 数据库表字段结构及记录在文件中的存储管理。要求设计表构造模式及其在数据库文件中的存储结构，最后在自选的软件平台上建立能创建、查看表构造模式的用户界面。先自定义表构造模式的结构，然后将其存放到自定义存储结构的数据库文件（`.dbf` 文件）中，要求能在一个数据库文件中存放多张不同的表。（提示：表构造模式包括字段名、类型、字长、是否为 KEY 键、是否允许为 NULL。考虑到以后对表的操作可以预留一些字段。）
2. 数据库表结构的创建及修改。在实验要求 1 的基础上，能对数据库文件内容进行读写，增加新的字段；删除字段；修改字段名、字段类型等。
3. 数据库表记录的插入、删除、修改及查询。设计记录在数据文件中的存储结构形式，并在自选的软件平台上建立用户界面来添加新记录到数据文件中，并能查看数据文件中的记录内容。根据从要求 1 中数据库文件（`.dbf` 文件）中抽取的有关表的构造模式信息，将记录存放到自设计存储格式的数据记录文件（`.dat` 文件）中，要求能存放不同的多张表的记录内容，能查看不同表的记录内容。
4. SQL 语句的实现。数据定义语言（DDL）的实现：实现定义表模式结构，并能修改表结构的语句。实现定义表（Create Table）；修改表（Edit Table、Rename Table、Delete Table）。数据操纵语言（DML）实现：实现记录数据的插入（Insert）、删除（Delete）、修改（Edit）。实现数据库单表、多表的选择、投影、连接查询（Select 条件查询）。
5. 界面设计。设计用户友好、操作方便和宜用的界面，兼具功能性和美观性。

# 四、报告正文

## 1. 系统需求分析

### 1.1 系统定位

本系统是一个**教学型单用户 DBMS**：不追求工业级数据库的并发、恢复与优化能力，而是完整展示“表结构如何存、记录如何存、SQL 如何解析执行、关系运算如何实现”这四个核心问题。系统的使用者是课程设计验收时的演示者，因此所有功能都要能通过界面直观地操作和观察。

### 1.3 数据需求

系统需要持久化两类数据：

1. **元数据（表结构）**：表名、字段名、字段类型、字长、KEY 标志、NULL 标志、VALID 标志；
2. **业务数据（表记录）**：各表的具体记录，按字段定长存放，另需一个有效标识数组支持逻辑删除。

两类数据必须能够“一个文件放多张表”，因此文件内部需要可识别的**表分隔标识**与**长度信息**。

### 1.4 界面与性能需求

- 界面：主菜单列出全部功能，操作有提示、有回显、有错误原因说明；查询结果以表格边框对齐显示；
- 容错：对非法输入（字段重名、类型不符、超出字长、KEY 重复、表不存在等）给出明确提示而不是崩溃；
- 性能：课程设计规模下（几十张表、几千条记录）各项操作应在可感知的瞬间完成。

### 1.5 约束分析

1. 由于要求把“表结构”和“表记录”分别放在 `.dbf` 与 `.dat` 两个文件中，且记录是定长存放，**记录文件的解析必须依赖结构文件提供各字段字长**，因此程序每次操作都先读 `.dbf` 再读 `.dat`，二者必须保持一致；
2. 字段的 `bValidFlag` 为“以后删除字段”预留，因此删除字段采用**逻辑删除**而非物理移动数据，避免破坏定长记录的对齐；
3. 记录的有效标识数组要求“记录总数”与“字段个数”先于记录内容书写，便于顺序解析。

## 2. 系统总体设计

### 2.1 设计目标与原则

- **分层清晰**：界面层不直接碰文件，存储层不关心 SQL，语义层负责把两者粘起来；
- **格式自描述**：文件按“标识 + 长度 + 内容”的顺序书写，可以顺序解析、可追加；
- **单一数据通路**：菜单操作全部转换为 SQL 字符串交给语义层执行，保证界面与命令行行为一致，减少重复代码；
- **可扩展**：结构体定义与文件格式为后续增加索引、事务、聚合函数预留了空间。

系统采用三层结构：

### 2.4 关键数据结构设计

**（1）字段结构（元数据的最小单位）**

与课程设计要求给出的结构完全一致：

```c
typedef struct {
    char sFieldName[15];  /* 字段名 */
    char sType[8];        /* 字段类型 */
    int  iSize;           /* 字长 */
    char bKey;            /* 是否 KEY 键 */
    char bNullFlag;       /* 是否允许为空 */
    char bValidFlag;      /* 字段是否有效 */
} TableMode;
```

**（2）内存中的表结构与记录**

程序运行期间使用 STL 容器组织数据，便于增删字段；写入文件时再转换成 `TableMode` 的定长形式，做到“内存灵活、磁盘紧凑”。

```c
struct FieldDef { string name, type; int size; bool isKey, allowNull, valid; };
struct TableDef { string name; vector<FieldDef> fields; };
struct Record   { vector<string> values; bool valid; };
struct Database { string name; vector<TableDef> tables; };   /* 一个 .dbf */
struct DataFile { vector<string> names; vector<vector<Record> > records; };  /* 一个 .dat */
```

### 2.5 文件存储格式设计

**（1）数据库文件 `.dbf`**

```
第一张表起始处：
  '~'（表分隔符，1 字节）
  表名（char[15]）
  此表所含字段个数（int，4 字节）
  第 1 个字段结构（TableMode）
  第 2 个字段结构（TableMode）
  ……
  第 n 个字段结构（TableMode）
第二张表起始处：
  '~' … 形式同前
```

**（2）数据文件 `.dat`**

```
第一张表的记录起始处：
  '~'（标识，1 字节）
  表名（char[15]）
  此表所含记录总数（int）
  记录的字段个数（int）
  各记录的有效标识（char[记录总数]，'1' 有效 / '0' 已删除）
  记录 1 的字段 1 … 记录 1 的字段 n
  记录 2 的字段 1 … 记录 2 的字段 n
  ……
第二张表的记录起始处：
  '~' … 形式同前
```

一条记录内各字段按**定义时的字长**定长存放，不足部分用空格补齐，读取时去除尾部空格。这样即使某条记录被删除，也能通过有效标识数组定位并跳过它。

### 2.6 主要流程

**建表流程**：菜单向导收集字段 → 拼成 `CREATE TABLE` 语句 → 词法/语法分析 → 检查重名与上限 → 追加到 `Database.tables` → 写 `.dbf` → 在 `.dat` 中建立该表的空记录段。

**插入流程**：读取 `.dbf` 得到字段（字长、类型、NULL、KEY）→ 校验值的类型与字长 → 检查 KEY 唯一性 → 追加记录 → 重写 `.dat`。

**查询流程**：解析出选择列、表列表、条件 → 载入相关表的全部有效记录 → 多重循环生成连接结果 → 逐行求值条件 → 输出投影列。

## 3. 系统详细设计

### 3.1 存储层详细设计

**（1）写入 `.dbf`**

按“表分隔符 → 表名 → 字段个数 → 字段结构数组”的顺序用 `fwrite` 顺序写出，每张表重复一次。表名固定占 15 字节，不足部分补 `'\0'`（便于 C 字符串读取）。

**（2）读取 `.dbf`**

循环执行：读 1 字节，若失败说明文件结束；若不是 `'~'` 说明文件格式损坏，报错返回；否则依次读表名、字段个数、字段结构数组。字段个数做了上限（50）校验，防止损坏文件导致越界。

**（3）写入 `.dat`**

对每张表依次写出：`'~'`、表名、记录总数、字段个数、有效标识数组、各条记录的各字段定长文本。写入前会把超长值截断、不足值补齐空格，保证字节布局严格对齐。

**（4）读取 `.dat`**

按同样的顺序解析。**关键点**：由于记录里不含字长信息，解析时必须先根据表名去 `.dbf` 中查出该表的字段字长；如果 `.dat` 中的表在 `.dbf` 中找不到，或字段个数对不上，就判定两个文件不同步并报错，避免按错误字长解析出垃圾数据。

**（5）表段的增删改**

- 新建表：`ensureTableSection` 追加一个空记录段；
- 改表名：`renameTableRecords` 修改记录段中的表名。**注意**：必须先用旧表名读完整个 `.dat` 再改 `.dbf` 中的表名，否则再读时会因名字对不上而失败；
- 删表：先读 `.dat`，再从 `.dbf` 删表、从 `.dat` 删段，最后分别写回。

### 3.2 词法分析

输入是一条 SQL 字符串，输出是记号（token）序列。

1. **全角归一化**：把 `（ ） ， ； ＝ ＞ ＜` 和全角空格替换为对应的半角字符，这样从课件里复制来的语句可以直接使用；
2. **扫描**：以空白为分隔；`( ) , ;` 各自成为独立记号；`= < > !` 参与组合出 `<=`、`>=`、`<>`、`!=`；单引号或双引号包裹的内容作为一个字符串常量记号；
3. 其余连续字符（如 `char[10]`、表名、字段名、数字）作为一个记号。

### 3.3 语法分析与语句执行

采用“**按首关键字分派 + 逐段解析**”的递归下降式写法，每个语句对应一个 `execXxx` 函数，成功后统一写出结果描述文本。

- `CREATE TABLE`：解析 `表名 ( 字段定义, … ) INTO 库名`，字段定义可带 `[字长]` 与若干标志位；
- `EDIT TABLE`：解析 `表名 ( 字段定义 ) IN 库名`，并按语义分三种情况处理——字段不存在则新增，存在则修改，`字段 RENAME TO 新字段` 则改名；
- `RENAME TABLE` / `DROP TABLE`：解析表名与库名，同步更新两个文件；
- `INSERT INTO … VALUES ( … ) IN 库名`：只对**有效字段**取值，个数必须与有效字段数一致；
- `DELETE FROM … [WHERE …] IN 库名`：先校验条件中引用的字段存在，再逐条求值；
- `UPDATE 表名 ( SET 字段=值, … [WHERE …] ) IN 库名`：允许多个赋值，赋值前做类型与字长校验；
- `SELECT 列 | * FROM 表[, 表…] [WHERE …]`：解析投影列与表列表，再进入查询执行。

**库名切换规则**：语句中带 `IN/INTO 库名` 时，如果与当前库不同就自动加载该库并切换为当前库；`CREATE TABLE … INTO 新库` 时若库不存在则新建。

### 3.4 条件表达式求值

条件解析为若干 `{左操作数, 运算符, 右操作数, 逻辑连接词}` 三元组：

- **操作数解析**：含 `.` 的按 `表名.字段名` 解析；不含 `.` 的在 FROM 列表的所有表中查字段，若在多张表中都出现则报“字段名不明确”；解析不到时按字符串常量处理，因此 `Name = ZhangSan` 也能工作；
- **比较规则**：双方都能识别为数字时按数值比较，否则按字符串字典序比较；任一侧为空值（NULL）时结果为假；
- **逻辑组合**：多条件按书写顺序从左到右用 `AND` / `OR` 组合。

### 3.5 连接查询的实现

SELECT 的执行过程：

1. 载入 FROM 列表中每张表的**有效记录**（空表用一个空指针占位，保证结果为空而不是出错）；
2. 用多重循环枚举各表记录的笛卡尔积；
3. 对每个组合建立"行上下文"，代入 WHERE 条件求值，通过的组合按投影列取值输出；
4. 结果集连同列名一起返回给界面层，由 `printQueryResult` 计算各列最大宽度后画框输出。

这是最直观的**嵌套循环连接**，复杂度为 O(∏|Ri|)，在课程设计的数据规模下完全够用；若需要优化，可以先按条件中的等值连接字段做哈希分桶。

### 3.6 界面层设计

- 主菜单显示当前数据库名与表数量，操作完成后回到主菜单；
- 建表、插记录采用**向导式**提问（逐字段询问类型、字长、KEY、NULL）并自动生成 SQL；
- 结果输出用 `+---+` 表格边框和列对齐，便于验收时展示；
- 所有错误都带上原因（如“违反 KEY 约束：字段 Sno 的值 1003 已存在”），便于定位。

### 3.7 关键算法伪代码

**插入记录**

```
读取表的字段定义 fields[]（只取 valid 的）
如果 值的个数 ≠ 有效字段数 → 报错
对每个字段 f：
    如果值为空 且 f 不允许 NULL → 报错
    如果 f 类型为 int/float 且值不是数字 → 报错
    如果 值长度 > f.字长 → 报错
如果 f 是 KEY 且库中已存在相同值 → 报错
把记录追加到该表的记录段，重写 .dat
```

**连接查询**

```
tabs[] = FROM 中的表
rows[i] = 表 i 的全部有效记录
for 每个 (r1, r2, …, rn) 组合:
    ctx = { tabs, (r1,…,rn) }
    if 条件为空 或 条件(ctx) 为真:
        out.push( 投影列取值(ctx) )
```

## 5. 系统总结

### 5.1 项目特点

1. **完全自定义存储格式**：从文件字节布局开始设计，能在一个文件中存放多张表；
2. **真正的 SQL 解析**：不是把菜单操作写死，而是实现了词法分析与语句分派，支持手写 SQL；
3. **分层清晰、职责单一**：存储层只关心字节，语义层只关心语句，界面层只关心交互；
4. **容错完整**：字段重名、类型不符、超出字长、KEY 冲突、表/库不存在等均有明确提示；
5. **可展示性强**：查询结果以表格边框对齐输出，便于验收演示。

### 5.2 局限与改进方向

| 局限 | 改进方向 |
| --- | --- |
| 记录定长存储，字段改字长会截断数据 | 引入变长记录 + 偏移表 |
| 每次修改都整体重写 `.dat` | 改为原地更新 + 空闲空间管理 |
| 只有嵌套循环连接 | 增加基于哈希的连接算法 |
| 没有索引 | 为 KEY 字段建立索引文件 |
| 不支持 `ORDER BY` / `GROUP BY` / 聚合函数 | 扩展语法分析与执行器 |
| 单用户、无并发与事务 | 增加日志与回滚机制 |
| 控制台界面 | 升级为 Qt 或 Web 图形界面 |

### 5.3 课程设计收获

通过本次课程设计，我们对“数据库管理系统到底做了什么”有了具体而直观的认识：表结构不过是文件里一段固定长度的结构体数组，记录的定位依赖字长与有效标识，而 SQL 语句本质上是被解析成一系列对文件的操作。亲手写出词法分析和连接查询之后，课本上“选择、投影、连接”这些关系代数运算不再是抽象符号，而是可以逐行调试的代码。同时，小组分工让我们体会到接口先行的必要性——正是因为一开始就约定了 `dbms.h` 中的数据结构与函数签名，各成员才能在各自的模块上并行开发。

## 附录 B：验收可能被问到的问题（准备）

1. **为什么记录文件里不存字段字长？** 因为课程设计要求 `.dat` 的结构只包含标识、表名、记录数、字段数、有效标识和记录内容；字长信息统一由 `.dbf` 提供，两个文件必须保持一致。好处是结构文件与数据文件职责分离，缺点是二者一旦不同步就无法解析，因此程序在读取时会做一致性校验。
2. **如何实现同一个文件存放多张表？** 用 `'~'` 作为表与表之间的分隔标识，每张表起始处先写表名，再写该表的字段个数（或记录数），之后紧跟具体内容，从而可以顺序解析出所有表。
3. **删除字段为什么不直接删除数据？** 因为记录是定长存放的，直接删除中间一列会导致后面所有字段错位；课程设计要求里也预留了 `bValidFlag`，因此改用逻辑删除，字段被标记为 INVALID 后不再参与查询，但数据仍保留。
4. **删除记录为什么也是逻辑删除？** 同理，`.dat` 中专门设计了“各记录的有效标识”数组，把对应字节置 `'0'` 即可，查询时跳过，必要时还可以恢复。
5. **连接查询是怎么实现的？** 先生成 FROM 中所有表记录的笛卡尔积，再用 WHERE 条件逐行筛选，最后按投影列输出。
6. **怎么保证 KEY 唯一？** 插入和更新时，若涉及 KEY 字段，会扫描该表所有有效记录，发现相同值就拒绝操作并报错。
7. **超出了字长怎么办？** 插入/更新时先校验，超长直接报错并提示字长限制，避免静默截断造成数据错误。
